01Purpose

SignalPlayback is a desktop application for building, storing, and replaying a library of time-domain signals. It gives an engineer one place to:

  1. Import recorded signals from a structured CSV format — grouped, with per-group and per-signal metadata.
  2. Generate synthetic signals from parameters: waveform type, frequency, amplitude, noise, modulation, composition.
  3. Persist everything into a durable, queryable local signal database.
  4. Play back signals on a time-synchronised on-screen scope with transport controls and multi-signal overlay.

The output of playback is on-screen visualization only. Hardware, network, and audio sinks are out of scope for v1, but the engine is structured so they can be added later as additional sinks.

02Goals and non-goals

Goals

G1 · Fidelity

Round-trip the CSV format losslessly. Import → database → export produces an equivalent file.

G2 · Scale

10 000 signals in a library, 100 M samples in a signal, without the UI dropping below 60 fps.

G3 · Reproducibility

A generated signal's parameter spec plus its stored seed regenerates bit-identical samples.

G4 · Portability

One executable plus a self-contained library directory. No server, no external database process.

G5 · Responsiveness

Every long operation is cancellable and reports progress without blocking the UI.

G6 · Inspectability

The database is readable and repairable with sqlite3 and a hex editor.

Non-goals for v1

  • Real-time output to DAC / SDR / DAQ hardware.
  • Network streaming of samples to other processes.
  • Audio playback.
  • Multi-user access, syncing, or a client/server split.
  • Heavy DSP analysis (filter design, demodulation chains). Basic FFT and statistics only.

Rejected alternatives

  • egui — better plotting out of the box, but immediate-mode redraw makes the transport and undo state model messier, and per-frame re-tessellation of 100 M-point traces is harder to cache than Iced's explicit canvas::Cache.
  • Tauri — richest charting ecosystem, but the IPC boundary would force sample data through serialization on every viewport change.
  • Pure-SQLite BLOB storage — simplest, but chunked BLOB reads add a copy per access and bloat the WAL during import.
  • DuckDB / Parquet-first — excellent for cross-signal analytics, heavier and awkward as live application state.

04Architecture

Crate layout

A Cargo workspace, so the domain logic is testable without a window.

Process and threading model

  • Single writer, many readers. WAL mode plus one dedicated writer thread eliminates SQLITE_BUSY retry logic entirely.
  • The UI never touches raw samples. The engine hands the canvas a ViewportSnapshot already reduced to roughly one min/max pair per horizontal pixel.
  • Cancellation via a token checked at chunk boundaries — every 64 K samples or 1 000 CSV rows — so cancel latency stays under about 50 ms.

06CSV import format

The file is a sequence of group blocks. Each block is a blank line, a group header row carrying a count column, a signal header row, one group data row, and then count signal rows — repeated for every group in the file.

Grammar

Parser behaviour

ConcernRule
Leading blank lineThe blank line is the block separator. A file that starts directly with a group header is accepted — an implicit separator is assumed at BOF.
Count columnLocated by case-insensitive name match against count, signal_count, num_signals, n_signals, nsig. Overridable per import profile.
Count mismatchStrict: error, abort the import. Tolerant (default): consume rows until the next blank line, record actual_count beside declared_count, raise a warning.
Samples in a signal rowColumns named in the signal header are metadata; every column beyond the header's declared arity is a sample. If the header itself carries sample columns (s0,s1,…), the profile marks where metadata ends and samples begin.
Alternate layoutA profile flag selects column-per-signal layout instead — the signal header names signals and each following row is one time step across the group. Both layouts share the block framer.
DelimiterAuto-detected from the first group header (, ; tab |), overridable.
EncodingUTF-8, with UTF-8/UTF-16 BOM stripped. Invalid sequences are reported with byte offsets, never silently replaced.
Line endingsLF and CRLF both accepted; a lone CR is treated as a line ending, with a warning.
CommentsLines starting with # are skipped everywhere except inside quoted fields. Configurable.
Missing valuesEmpty, NaN, NA, null → f64::NAN, drawn as a gap in the trace.
Numeric parsingDecimal and scientific notation. Thousands separators rejected. Locale-independent: always . as the decimal point.
ErrorsEvery diagnostic carries block index, line number, byte offset, column index and message, and appears in a scrollable error panel with a jump-to-line action.

Import pipeline

The sniff pass reads only enough to show a preview table and suggest a profile, so a 4 GB file feels instant to open. The ingest pass streams the whole file once, writing sample blobs incrementally and holding at most one group in memory.

Import is transactional at the dataset level: a failure rolls back the SQLite rows and deletes any orphaned blobs.

Export

The writer reverses the grammar exactly, preserving original column order and unmapped attributes from the attributes JSON — this is what satisfies G1. A round-trip fixture set lives in crates/sp-csv/tests/fixtures/.

07Signal generation

Spec model

A generated signal is described by a serialisable DAG stored as JSON in signal.gen_spec. Samples are a cache of the spec, so deleting a blob is always safe.

Rendering

  • A pure function render(&GenSpec, range) -> SampleBuffer, so any window can be produced independently. Rayon splits the range across cores.
  • Noise nodes derive a per-node stream by hashing (seed, node_path). A range rendered in parallel chunks matches the same range rendered serially, and adding a node elsewhere in the tree does not perturb an existing node's noise.
  • Parameter validation happens up front: negative frequencies, duty outside (0, 1), and Nyquist violations (freq_hz ≥ fs/2) become blocking errors with a suggested fix.

Generator UI

  • Left: a node tree with add, remove, reorder. Right: parameters for the selected node.
  • A live preview strip renders the first ~2 seconds at reduced rate on every keystroke, debounced 150 ms, so the shape is visible before committing.
  • Sweep mode: mark one numeric parameter as swept — start, stop, step, or an explicit list — to emit a whole group in one action, e.g. 20 sine waves from 100 Hz to 2 kHz. The sweep becomes a signal_group with the swept value in attributes.
  • Presets are GenSpec JSON files; a small built-in library ships with the app.

08Playback engine

Transport state machine

Clock

Playback time is decoupled from frame rate. Each tick:

  • A monotonic Instant avoids wall-clock jumps.
  • If dt_wall > 250 ms — window unfocused, breakpoint hit — the tick is clamped rather than applied, so the playhead does not teleport after a stall.
  • At the loop end: wrap to loop start (Loop), clamp and pause (Once), or reverse (PingPong).
  • Ticks are driven by an Iced subscription on window redraw requests, so the engine never runs faster than the display and idles at zero CPU when paused.

Timeline and alignment

All signals map onto one absolute timeline in seconds. A signal's sample i sits at t = t0_s + i / sample_rate_hz, or at time_blob[i] when irregular. Signals with different rates therefore overlay correctly with no resampling. A playlist's t_offset_s nudges an individual trace for manual alignment.

Scope rendering

Two display modes: playhead mode, where the viewport is fixed and a vertical cursor sweeps across it, and scrolling mode, where the playhead is pinned near 80% width and the window scrolls under it like a strip-chart recorder.

Rendering runs in three Iced canvas layers, so a moving playhead never re-tessellates the traces.

Interactions. Scroll zooms time about the pointer; shift+scroll pans; ctrl+scroll zooms amplitude; drag is a box zoom; double-click fits; Home/End jump to bounds; space toggles play/pause; [ and ] set the loop in and out points.

Per-trace controls. Visibility, colour, gain, vertical offset, and a stacked vs. overlaid layout toggle — stacked gives each signal its own horizontal lane.

Application shape

UX principles

  • No modal blocking on IO. Import and generation run in the background; the library stays browsable.
  • Destructive actions confirm, and undo where it is cheap. Delete moves to a session trash table; permanent delete is a separate explicit action.
  • Errors are data, not dialogs. Import problems land in a filterable list the user works through, not a popup per row.
  • Keyboard first for transport and navigation. Every action has a shortcut.

11Cross-cutting concerns

Error handling

A thiserror enum per crate; sp-app maps them to user-facing text. Nothing panics on bad input — a corrupt CSV or a truncated blob produces a diagnostic. Panics inside worker tasks are caught at the task boundary and reported as a job failure.

Integrity

Blob checksums are verified on first read after app start and after any crash recovery. A Verify Library action rehashes everything and reports mismatches in both directions — rows without blobs, blobs without rows.

Testing

  • Unit tests per crate; proptest properties for the CSV round-trip (G1) and for generator determinism across chunk boundaries (G3).
  • Golden-file tests for the parser against a fixture corpus that includes malformed files.
  • sp-engine transport tests drive the state machine with a mock clock — no UI needed.
  • A headless smoke test opens a library, imports a fixture, and renders a viewport.

Observability, distribution, accessibility

  • tracing spans around every job, a Log panel in the app, and a rolling file log in the library root. --verbose raises the level.
  • cargo build --release produces a single .exe. Windows is the primary target; Linux and macOS build from the same source, since every dependency is cross-platform. An optional MSI via cargo-wix later.
  • Trace palettes are colour-blind-safe by default (Okabe–Ito). Trace identity is also carried by a legend and line style, never by colour alone. Minimum 14 px UI text, full keyboard navigation.

14Assumptions and open questions

Confirm before M2

Items 1–4 concern the CSV format and change the design materially. A single real sample file settles all four.

  1. Block row order. This document takes the stated order literally: group header → signal header → group data row → signal rows. The more conventional layout would put the group data row immediately after the group header. The framer will auto-detect both, by testing which row's arity matches which header, but a sample file would settle it.
  2. Where samples live in a signal row. Assumed: each signal row is one complete signal, metadata columns first and sample values trailing. The alternative — the signal header names the signals and each following row is one time step — is supported via a profile flag, but only one should be the default.
  3. Timebase source. Assumed the sample rate comes from a group-level column and the time axis is implicit. If files instead carry an explicit time column per signal, time_blob_id covers it, but the mapping UI needs a “this column is time” affordance.
  4. Group count semantics. Assumed to be the number of signal rows in the block. If it means samples per signal instead, the framer's block-termination rule changes.
  5. Numeric precision. Default storage is f32 — half the memory, ample for most captured signals — with f64 available per signal. Confirm f32 is an acceptable default.
  6. Library scale. The design targets 10 000 signals and roughly 100 GB of samples. An order of magnitude beyond that would argue for a columnar store instead.
  7. Complex signals. c64 is reserved in the dtype enum but not implemented in v1. Confirm whether I/Q pairs arrive as two real signals, as assumed, or as one complex signal.
